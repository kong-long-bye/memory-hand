> 对照材料：Agent Memory Leaderboard 代码记忆榜首期**开源榜**头部方案分析（causal-memory / Memoria / agent-memory 等 8 个并列第一）

## 1. 榜首告诉我们的三件事

### 1.1 成绩极度收敛，说明"再加一层抽象"没有收益

| 方案 | 核心思路 | Task Solve | New Feature | Bug Fix |
|---|---|---:|---:|---:|
| causal-memory | 保留原始历史 + 词法与语义双路融合 | **52.67%** | **62.75%** | 47.47% |
| Memoria | 混合检索 + 代码场景 token（函数名/路径/异常）+ 命中的**邻近平滑** | **52.67%** | 60.78% | 48.48% |
| agent-memory | 纯 Raw-First，BM25 + 本地 Dense 融合 | 52.00% | 50.98% | **52.53%** |
| 另有 5 个方法 | 并列第一 | 52.67% | — | — |
| agent-memory 之后的一档 | ChronoHybridMem / mem0-BQE / MemoryBear 等 | 52.00% | — | — |
| 工业榜最高 | — | 62.00% | — | — |

头部十几个方案总分开差**不到 1 个百分点**。这是一个很强的信号：**胜负点不在"记忆被加工得多精巧"，而在"检索把哪些信号用上了"**。我们 README 里那句"胜负点不是 Vector Database，而是 Memory Ranking"和榜单分布完全一致，可以保留。

### 1.2 三个代表方案没有任何一个用 LLM 摘要替换原始历史

文章的原话是"对历史做更复杂的预先抽象，并不是取得较好成绩的必要条件"。注意措辞是**不必要**，不是**有害**。榜单证明的是：raw + 把检索做好，就能到第一梯队。

### 1.3 评测目标已经从"召回多少"变成"任务能不能做完"

评价口径是 Task Solve（解题完成率），不是 Recall@k。这条决定了我们后面所有改进的验收标准：**指标涨但返回内容平台模型用不上，等于白做。**

## 2. 我们现在的做法（代码即事实）

```
/add  ──►  messages[].content 换行拼成一条 content ──►  原样 append 到 memory.jsonl
                                                          （timestamp 丢弃）
/search ──► 按 user_id 取该桶文档 ──► 首次查询时懒建 BM25Okapi ──► 全量文档按原始分数排序
                                                              ──► 无条件返回 top_k 条完整原文
```

- **存储**：Raw-First，✅ 和榜首三条路线一致，没有被摘要污染。
- **分词**：[memory_engine.py:159-193](../src/memory_engine.py#L159-L193) 已经把 `snake_case` 拆词、`CamelCase` 拆词（含 `HTTPResponse → HTTP|Response` 缩写边界）、中文 jieba。这一步其实已经踩在 Memoria 的思路上了，只是只做了一半。
- **检索**：**只有一条 BM25 通道**。榜首 8 个方案全部是双路以上融合。
- **排序**：[memory_engine.py:111-126](../src/memory_engine.py#L111-L126) 直接返回 BM25 原始分数排序后的 top_k，**没有相关性阈值，也没有分数归一化**（低分噪声一定占满 Top-K；`rank_bm25` 的负 IDF 兜底还会让高频词把文档分数拖成负数）。
- **返回**：完整原文。`top_k` 默认 100（[app.py:42](../src/app.py#L42)），单条 smoke 轨迹 5.6 万 ~ 40 万字符 → 一次响应实测过 721,656 B。

### 本地基线（lite，`reports/eval_swe_lite_local_20261011_103757.json`）

| 条件 | pool | Recall@1 | Recall@10 | MRR | noise@10 | hn_rejection@10 |
|---|---:|---:|---:|---:|---:|---:|
| relevant | 71 | 0.7424 | 0.9394 | 0.8066 | 0.9051 | 0.0505 |
| noisy | 300 | 0.5354 | 0.8485 | 0.6449 | 0.9141 | **0.0000** |

读法：**Recall@10 已经不差了，真正的洞是"池子一大，Top-1 就排不准"**（0.74 → 0.54），以及 noisy 下每个任务的 Top-10 里都混进了同仓库的非 gold 经验。这正是榜首方案用"多信号融合 + 实体匹配"要解决的那类问题。

## 3. 逐项对比：差在哪

| 维度 | 榜首头部 | 我们现状 | 差距 | 本地能不能测出来 |
|---|---|---|---|---|
| 原始信息保留 | 3/3 都 Raw-First | ✅ Raw 入库，无 LLM 加工 | 无 | — |
| 检索通道 | BM25 + Dense（+ 实体）融合 | ❌ 只有 BM25 | **结构性缺失** | ✅ Recall/MRR |
| 代码 token | 拆词 **+ 路径/函数/异常当独立信号加权** | 🟡 只拆词，不抽实体、不加权 | 半个 | ✅ Recall/MRR |
| 命中后邻近平滑 | Memoria 明确用命中记录附近历史消息补上下文 | ❌ 完全没有 | **缺失** | ❌ 只有官方 smoke 能测 |
| 尾部方案段 | 原始记录整条保留 | ❌ 整条返回时被截，改法恰好丢掉 | **已知致 0 分** | ❌ 只有 smoke 能测 |
| 低分噪声控制 | 多信号交叉抑制 | ❌ 无阈值、负 IDF 未修 | 缺失 | ✅ MRR/Recall@1 |
| 按任务类型组织经验 | 榜单把 New Feature / Bug Fix 拆开呈现差异 | ❌ 一视同仁，且本地数据无标签 | 缺失 | 🟡 需先加标签或做诊断 |
| 试错链（失败尝试） | 文章结论"减少重复试错" | ❌ 时间戳入库即丢，无法串链 | 缺失 | ❌ |
| 响应体积 | 未披露，但答案侧有统一 LLM 预算 | ❌ raw 全文 + top_k=100 | **我们独有风险** | ✅ 响应字节数 |

一句话：**我们不是"抽象层太少"，是"检索信号太少 + 返回内容不可用"**。原计划里 Day 2 的 LLM 摘要已经被 PLAN_10_DAYS.md 改成"摘要不进主链路"，这个修正方向是对的，榜单经验支持它。

## 4. 必须先讲清一件事：官方 smoke 集和本地数据集是两种形态

这一点直接决定改进顺序，之前踩过坑都在这里。

```
本地 SWEContextBench 一条经验            官方 smoke 一条轨迹（data_store 现有 6 条，56,100~397,632 字符）
┌────────────────────────────┐          ┌──────────────────────────────────────────────────┐
│ problem_statement          │          │ # Issue                                          │
│ -------------------------- │          │ # Your task                                      │
│ gold patch（整条）          │          │ 探索转录（几十万字：读文件、试错、报错、失败尝试）│  ← 98% 长度
│                            │          │ ## Changes / ## Root Cause / ## Fix              │  ← 只有末尾 1~4KB
└────────────────────────────┘          └──────────────────────────────────────────────────┘
一条 = 一条经验，彼此无相邻关系          一条 = 一条巨型轨迹，"改法"永远压在尾部
```

- **SWEContextBench 测的是"检索排序准不准"**：每条经验独立入库，没有"相邻记录"概念，所以邻近平滑这类改动在 lite 上**指标不动**，不能因此判定它无效。
- **官方 smoke 集测的是"平台解题模型拿到的上下文里有没有改法"**：smoke 曾出现「文件定位率 100.00 / 解题成功率 0.00」，而 BM25 排序本身是对的（gold 排第 1）。原因就是把整条轨迹原样返回、被答案侧预算截断，恰好截掉尾部 1~4KB。
- **两套数据共用的口径见 §4.1**（官方怎么跑、怎么打分，以及为什么 `noise@10` 高不是故障）。
- 结论：**任何"返回视图"的改动，必须同时在 smoke 集（看解题率是否 >0）和 SWEContextBench（看 Recall/MRR 是否回退）两处验收**，只看一处都会误判。

### 4.1 官方的运行与评分方式（本期）

- 参赛方只做 **Add / Search**；平台侧**解题 Agent 在处理代码仓库和任务时调用 Search**，把返回的历史经验当辅助上下文。
- Agent 最终要在**隔离环境里真的改代码**，平台用**任务验证程序**判断补丁是否解决问题 —— 分数是"补丁通过没有"，不是召回率。
- 本期 **150 个基础任务**，每题在 `relevant` 与 `noisy` 两种记忆条件下各跑一次 = **300 个评测单元**；
  这两个条件是**记忆环境**（池子里有没有无关经验），**不是难度等级**。

三条推论（决定了改进顺序）：

1. **`noise@10` 高不是故障，不能当优化目标。** 池子 300 条而 gold 平均 1~2 条，Top-10 里必然有 8~9 条非 gold（本地 noisy `noise@10 = 0.9141`）。拿它去优化会把 gold 一起砍掉；该盯的是 **Recall@k / MRR** 和**返回内容里到底有没有改法**。
2. **得分路径是"上下文 → 补丁通过验证"**，所以改进 1（让已召回的东西真的可用）直接压在得分路径上，Recall 只是它的代理指标。这也是把改进 1 排在 Dense 之前的理由。
3. 本地 lite 是 99 题 × 2 = 198 单元，`dataset_adapter.CONDITIONS` 已按官方的 relevant/noisy 同形态构造，可当作 150 题的缩小代理；但**它是检索代理，不是完成率代理**。

## 5. 改进清单（按优先级，第一改什么、第二改什么）

> 验收口径见 §4.1：官方按"隔离环境里补丁能否通过任务验证"打分，`relevant`/`noisy` 是记忆环境而非难度等级。

### 前置（半天，地基，必须先做）✅ 已完成

**把检索结果做成可追溯的 ID 映射。**

[evaluate.py](../src/evaluate.py) 原来靠"返回的 `content` 完全等于原文"反查经验 ID。这意味着：只要下一条改进开始分块、加视图、加标记，评测立刻全量变 `<unmapped>`，指标假死。

已落地的做法（改动 2 个文件，约 30 行）：

- [memory_engine.py:37-43](../src/memory_engine.py#L37-L43) 新增 `memory_id(content) = "mem_" + sha256(content)[:12]`，写入时用它当记忆 `id`（[memory_engine.py:87](../src/memory_engine.py#L87)）。契约字段不变，`/search` 本来就返回 `id`。
- [evaluate.py:69-82](../src/evaluate.py#L69-L82) 的映射键改成该 id；每任务新增 `n_unmapped`，summary 里给总量（门槛要求 = 0）。

验证（临时 store，**不碰 `data_store/memory.jsonl` 里的官方 smoke 数据**，事后已删）：

| split | 记忆数 | 命中数 | unmapped | 与旧 content 全等口径的排序差异 |
|---|---:|---:|---:|---:|
| lite / noisy | 300 | 990 | **0** | 0 / 99 任务 |
| full / noisy | 1007 | 3570 | **0** | 0 / 357 任务 |

即：**映射换了地基，指标一位没变**（BM25 与分词未动），后续分块/视图改动才具备可验证性。顺带核实：两个 split 的池子都**没有重复 content**（映射键唯一）；`self_hit` 在 lite 为 0、在 full 为 1（`django__django-13658`），丢弃自命中的分支只对 full 有意义。

已做（第二轮补上）：**同一 `user_id` 内同内容判重**（换 `request_id` 重发不再白占 Top-K 名额、不再稀释 IDF）+ **`timestamp` 落库**（`/add` 的 `messages[].timestamp` 取最大值存进记录，跨记录邻近平滑的顺序信号）。
**跨 `user_id` 去重确认不做**：索引按 user_id 隔离，跨 user 重复对检索零影响，只省磁盘 —— 真实 smoke 文件 44.9% 的字节是重复，但重复全在跨 user 上，压缩它换不来任何指标。

两个必须记住的副作用：

1. **旧库里的记录 id 与新规则不兼容**。`data_store/memory.jsonl` 现有 6 行是 uuid 形式的旧 id，用新 `evaluate.py` 直接评会全量 `<unmapped>`。正式基线必须用新 `run_id` 重新 `/add`，不要拿旧文件评。
2. **内容寻址 id 会让"同内容重复写入"得到相同 id**（跨 `user_id` 本就相同，这是去重的基础）。同一 `user_id` 内以不同 `request_id` 写入同一份原文的情况已在写入侧堵住（`add` 判重直接跳过），老库里若已有这种重复行，`_load` 也会丢弃、不进索引。

### 改进 1：让"已经召回对的东西"变成平台能用的证据

**改什么**：`/add` 时把超长轨迹切成带序号的块（同一条记忆保留 `source_id` + `chunk_index`），`/search` 命中某块后，把**同一条记忆的相邻块**一起给出，并保证尾部方案段一定进入返回；整体受一个明确预算约束，超预算按块丢而不是按字符截断。

**为什么排第一**：榜首的结论是"记忆的价值在于减少重复试错"，而我们唯一被证实的 0 分原因就是"排序对了、内容丢了"。Memoria 把"命中记录附近的历史消息补充上下文"写进了方案描述，这是榜单里唯一直接对应我们已知失败的机制。而且它不需要模型、不需要 LLM，纯确定性规则，风险最低。

**怎么验收**：smoke 集看解题成功率是否从 0 抬起、文件定位率不掉；SWEContextBench lite 看 `recall@10` 相对 V0 回退 ≤0.02、`unmapped=0`、`n_returned` 仍满足 `top_k` 语义（历史上预算设 12000 时曾把 `top_k=10` 静默砍成 3~4 条，`recall@10` 从 0.9394 掉到 0.8586 —— 这类回退必须用 `n_returned` 才能看出来）。

### 改进 2：补第二条检索通道，做 BM25 + Dense 的 rank 融合

**改什么**：本地小模型出 embedding + 向量索引（按 `user_id` 隔离），BM25 top-N 与 Dense top-N 用 RRF 融合去重，去重按经验 ID 而不是按文本。

**为什么排第二**：榜首 8 个并列第一里，词法 + 语义双路是共同项，没有一个只靠 BM25。我们的 `relevant` 0.7424 与 `noisy` 0.5354 之间那 0.21 的落差，本质是纯词法在大池子里被长词重合误导；语义通道正是补这个的。`hn_rejection@10 = 0.0000`（noisy 下每个任务 Top-10 都混进同仓库非 gold）也说明单靠词法分不出"同仓库里哪条真的相关"。

**注意**：agent-memory 用的是 **local** dense retrieval，不是外部 API。这条路线对我们尤其重要——模型必须离线打进镜像或挂载持久目录，HF 缓存放项目内（不要写 C 盘默认路径）。同时要把冷启动加载耗时、索引体积、内存占用一起记进报告，否则 V7 的 SLA 兑现会被这步拖垮。

**先单独证明它有用再做融合**：Dense-only 先完整跑一遍 lite，如果它在 noisy 上没有任何增益，就不要为了"听起来先进"把它塞进主链路。

### 改进 3：把代码实体变成检索信号（同时修 BM25 的两个已知毛病）

**改什么**：`/add` 时用正则/规则（**不用 LLM**）抽出四类实体存进 `metadata`，并让它们以更高权重进入 BM25 语料：

| 实体 | 例子 | 对谁最有用 |
|---|---|---|
| 文件路径 | `django/db/models/fields.py` | Bug Fix（改过哪里） |
| 函数/类 | `refresh_cache`、`QuerySet` | 两类都需要 |
| 异常名 | `ValueError`、`TimeoutError` | Bug Fix（报错匹配） |
| patch 改动位置 | `+++ b/...`、hunk header 里的函数名 | 判断这条经验是否真改到点上 |

同版本顺手做两件清理：`rank_bm25` 的负 IDF 兜底会把命中高频词的文档排到最后（排序方向不可信），需要在自己这层做查询内归一化；以及加一个 `min_score_ratio` 低分过滤实验，把噪声挡在 Top-K 外——**但过滤不能牺牲 gold，必须同时报"被过滤掉但实际是 gold 的任务数"**。

**为什么排第三**：这是 Memoria 拿 48.48% Bug Fix 的核心机制，纯规则、成本最低（一天可完成）、对 `noisy MRR` 这种已知短板最直接。它排在改进 2 之后只是按"榜单证据强度"排的；**如果你只有两天时间，可以把这条提到改进 2 前面**，因为它不引入模型体积和冷启动风险。

### 改进 4：按任务类型把结果拆开看，再谈差异化召回

**改什么**：先在 `evaluate.py` 里按查询意图把指标分两组输出（规则分类，含异常/堆栈/`fix|bug|error|异常` → Bug Fix；含 `add|implement|支持|新增` → New Feature），确认两类任务的失败模式是否真的不同；只有诊断成立，才做"Bug Fix 提高 errors/files 权重、New Feature 提高语义权重"的差异化排序。

**为什么排第四（以及一个诚实的前提）**：榜单把 New Feature / Bug Fix 拆开后差异很明显（causal-memory 62.75/47.47 对 agent-memory 50.98/52.53），这是总分挤在 1 个百分点内**少数还能拉开空间的维度**，属于我们的差异化机会。但 **SWEContextBench 里没有可靠的 New Feature / Bug Fix 标签**，平台侧也不保证给得到；所以现在做这件事只能是诊断实验，不能包装成"已实现任务感知能力"。先分类、先量指标，再动权重。

### 改进 5：试错链信号与工程容量

**改什么**（两件，都是榜单结尾那句话的直接回应，但分数收益不如前四条确定，所以放最后）：

- **试错链**：把轨迹里"失败尝试 → 最终修复"完整链条当作可加分信号（依赖前置里的 `timestamp` 与 chunk 序号）。文章结论"Memory 正在从记住过去走向减少重复试错"指的就是这个，但它需要改进 1 的分块先落地。
- **工程侧**：`/add` 不再每次令整个用户索引失效（增量或分桶重建）；`/search` 不要在写锁内做全量重排；幂等要能让客户端区分"新写入"与"重复请求"；`/search` 默认 `top_k` 从 100 降到与响应预算匹配的值，并在提交材料里把响应字节数写成申报依据而不是照抄 README。

## 6. 明确不做的事

- ❌ 用 LLM 摘要**替换**原始记录入库。榜首没有任何一个头部方案这么做，我们自己也已经因网关不稳定（404 model_not_found、推理模型 200 空返回）吃过亏；摘要最多作为叠加视图进 A/B。
- ❌ 只回"三段卡片"而有损压缩。卡片保住了尾部方案段，但丢掉了轨迹中部的报错原文、失败尝试与修改路径——那正是 Bug Fix 最有价值的部分。改成"卡片/锚点 + 邻近平滑 + 原始片段引用"。
- ❌ 在检索与排序之外再堆框架层。分数收敛到 1 个百分点以内，说明加层没有边际收益。
- ❌ 在 Full 上反复调参、或针对公开题硬编码（红线，判废）。

---

## 7. 对当前 `PLAN_10_DAYS.md` 的修订意见

现在的 V0→V7 路线大方向和经验一致（Raw-First、每版必须过 paired 门槛、Dense 先单测再融合），只需要调整三处顺序：

| 计划里 | 建议 |
|---|---|
| V1（BM25 变体与低分过滤）先做 | 保留，但**改进 1（分块 + 邻近平滑 + 证据视图）提前**，因为它是唯一对应已知 0 分的改动 |
| V6 才处理 compact 响应视图 | 提前与改进 1 合并 —— 视图与平滑是同一件事的两面，分开做会重复返工 |
| 评测靠 ID 还是靠 content | ✅ 已改成显式 ID（内容哈希）映射，lite/full 全量 `unmapped=0` 且排序与旧口径逐项一致；分块落地时再把映射表升级成 `(memory_id, chunk_index) -> 经验 ID` |
| 验收口径 | 每版报告除 Recall/MRR 外，必须同时记 **响应字节数** 与 **尾部方案段是否进入返回**；这两项才是 Task Solve 的直接代理 |

## 8. 一句话结论

榜单经验给的不是"去上向量数据库"，而是三条可执行原则：**别把原始信息加工掉、把检索信号做厚、让返回内容真的被用起来**。我们第一条已经做对了，第二条缺一半（无 Dense、实体只拆词不加权），第三条是已知失分点（巨型轨迹被答案侧预算截断、改法落在尾部）。

所以改进顺序是：**先让结果可追溯 → 再让召回对的东西变成可用证据（分块 + 邻近平滑 + 预算）→ 补 Dense 与 RRF → 把路径/函数/异常做成检索信号并修 BM25 噪声 → 按 New Feature / Bug Fix 拆开诊断 → 最后做试错链与容量工程**。

其中前四条都能在本地 SWEContextBench lite 上量出指标变化，改进 1 与 4/5 必须额外用 `data_store` 里的官方 smoke 轨迹验收（那才是测"解题率"的唯一数据集），只看 lite 会误判成"改了没效果"。
