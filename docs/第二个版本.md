# 记忆检索系统 V2：BM25 + Dense + Evidence Builder 工程改造方案

> **文档性质**：可执行的代码改造设计 / 开发任务书（尚未修改上传源码）  
> **基线**：`src.zip` 中 `src/memory_engine.py`、`src/app.py`（V1.1）  
> **其他输入**：`memory.jsonl`、`official_search_qa.jsonl`、`bm25_memory_search_roadmap_v1.1-v1.5.md`，以及本轮给出的六层架构图  
> **目标版本**：V2.3 = BM25 + Dense + RRF + Evidence Builder  
> **日期**：2026-10-20  
> **基本原则**：检索层提供**有出处、面向工程任务的证据包**；Agent 负责推理、修改与验证。检索层不得伪造历史补丁、测试或“已修复”结论。

---

## 0. 一页式工程决策

### 0.1 目标

将当前的

```text
query → BM25 message 搜索 → Parent 最高分 unit → [role] + 原文 → Agent
```

改造成

```text
                      ┌── BM25：精确匹配 ────┐
Agent Search Query ───┤                     ├── RRF（按统一证据 unit 融合）
                      └── Dense：语义召回 ──┘
                                   │
                         Parent 候选与 anchor
                                   │
                 Evidence Builder（新增核心）
                  ├─ 源消息/证据解析
                  ├─ 同任务证据关联（不是滑窗）
                  ├─ 去重与证据覆盖
                  ├─ 来源偏移校验
                  └─ 预算分配
                                   │
             Structured Engineering Context（字符串）
           Problem | Source | Error | Patch | Test | Summary
                                   │
                官方 /search → Agent 自主修复
```

**本次重要决策**：

1. **BM25 保留**：符号、文件路径、异常名的精确匹配不能丢。
2. **Dense 增加而不替换**：解决不同自然语言表述、相邻设计上下文的语义召回。
3. **不把 Dense 当成答案生成器**：Dense 找到候选，不能创造历史中没有的补丁。
4. **Evidence Builder 是成败关键**：按任务相关性从同一个 Parent 内选出多条互补证据，而不是最高分命中再加固定滑窗。
5. **最终接口完全兼容**：`/add`、`/search`、Parent ID、`top_k`、60,000 字符总预算不变。
6. **分阶段评测**：V2.1 测证据组装、V2.2 测 Dense、V2.3 测组合；不将多个变量混在同一对照实验中。

### 0.2 本次数据的现实边界

- 在本次 Astropy `required-columns` 问题的原始记忆里，存在 `_check_required_columns()` 的源码线索。
- 未找到针对**该具体问题**的历史修复 diff 与相应回归验证。已有 `to_pandas()` 补丁属于不同任务。
- 因此，此案例应该输出**诊断型证据包**而不是“已验证的历史修复答案”。
- Agent 仍可能基于源码线索自行修复；不能把“历史没有现成补丁”直接解释为“本题不值得评测”。

**现有源码与旧 roadmap 的一处不一致**：`search()` 中第 236–245 行按 `query_set & unit_set` 判断词面重叠，**没有**使用 `score < 0` 过滤。旧文档“负分 unit 不返回”应更正，以代码为准。

### 1.2 不可破坏的外部契约

```json
{
  "data": [
    {
      "id": "mem_...",
      "content": "[source | m=75]...\n[error | m=...]...",
      "score": 0.0328,
      "created_at": "2026-10-17T00:00:00Z"
    }
  ]
}
```

- `/add` 与 `/search` 请求和返回**字段不变**；`content` 继续为字符串。
- `data[i].id` 仍是 Parent Memory ID，绝不是向量 ID 或 chunk ID。
- `len(data) <= top_k`；每个 Parent 最多返回一次，不为了凑满 `top_k` 添无关内容。
- 每个 `content` 仅引用**该 Parent** 的消息片段；禁止混合不同 Parent 的正文。
- 严格按 `user_id` 隔离；不能靠 `session_id` 跨用户查找。
- `sum(len(item["content"]) for item in data) <= 60000`，**包括所有标签与换行**。
- 所有正文证据都可回查 `message_index + start + end`，不添加未经历史支持的工程结论。
- `score` V2.2/2.3 采用融合后分数，数值**不与 V1.1 BM25 原分值横向比较**。

## 2. 模块一：Agent Search Query

### 目标

把一个自然语言工程问题提取成**检索线索**，不是用 LLM 生成答案。

### 内部结构（不改变官方请求）

```python
@dataclass(frozen=True)
class QueryFeatures:
    raw: str
    tokens: tuple[str, ...]       # 现有 tokenize()
    file_paths: tuple[str, ...]   # astropy/timeseries/core.py
    symbols: tuple[str, ...]      # _check_required_columns
    error_names: tuple[str, ...]  # ValueError / AssertionError ...
    test_paths: tuple[str, ...]   # tests/test_*.py
    intent: str                   # bugfix / explain / implementation / unknown
```

- `raw` 始终保留用户传入的 query，不改写。
- 使用轻量正则/规则提取文件路径、`def`/类/方法名、异常名、测试名；不调用生成式 LLM。
- `intent` 只用于选择证据类型的优先顺序。无法确定时用 `unknown`，不可把启发式意图当作事实。
- `SearchRequest.options` 当前虽然定义了却没有参与搜索；本次不依赖它，不擅自改变其含义。

### 验收

空 query 返回空；包含 `_check_required_columns` 的 query 应保留这个**完整符号**，不能仅保留分词后的 `check/required/columns`。

## 3. 模块二：BM25 + Dense 双路召回

### 3.1 统一检索单元与来源定位

两路搜索必须能指向同一份**原始消息**，不允许 Dense 仅返回一段失去来源的相似文本。

```python
@dataclass(frozen=True)
class UnitRef:
    user_id: str
    parent_id: str
    message_index: int
    start: int
    end: int
    role: str
    unit_id: str  # 稳定标识；源头来自上述键，而非数据库行号
```

统一键的组成是 `(user_id, parent_id, message_index, start, end)`。跨用户 Parent ID 恰好相同也不能共用**检索命中空间**。

- **BM25**：V2.1 继续使用当前 message / 超长 message 内分块的 unit。
- **Dense**：优先为同一 canonical unit 生成 embedding。如果该 unit 超出 embedding 模型输入限制，则在其内部进一步切短子块；检索命中可带子块偏移，但在 RRF 中映射回 canonical unit，避免两路永远匹配不上。
- 同时保留 Dense 子块位置供 Evidence Builder 精确抽取。内部 embedding 子块不得跨 message。

> **为什么不是直接对整条 Parent 做 embedding？** 当前 Parent 可能混有多个不同工程任务。整条对话向量会稀释局部问题，且难以回溯到正确的代码和测试消息。

### 3.2 BM25 路径

新增（或从 `search()` 提取）：

```python
def search_bm25_units(index, query_features, top_n=40) -> list[UnitHit]:
    # 沿用 V1.1 BM25Okapi、tokenize 和词面重叠筛选
    # 不在这里按 Parent 丢弃多余命中
    # 输出 unit_ref、raw_score、rank、channel="bm25"
    ...
```

- 继续对 BM25 分数做降序排序。
- 只保留存在词面交集的候选，以保持基线意义。
- 输出 Top-N **unit**，不要先用 `best[mi]` 每个 Parent 只留一个。
- V2.1 **用于排序的 Parent max 逻辑保持**；把多 unit 留给组装器是内容选择的实现方式，不改变 Parent 的基线排序实验。

### 3.3 Dense 路径

推荐新增 `src/embedding_client.py` 和 `src/dense_index.py`。

初始配置继承现有 roadmap：

| 项目 | 初始值 / 规则 |
|---|---|
| Embedding model | `text-embedding-v4`（由实际服务商/部署环境确认） |
| Embedding dimension | 目标 1024；实际先探测、强校验 |
| BM25_TOP_N | 40 |
| DENSE_TOP_N | 40 |
| 文档 embedding batch | 8（不超过当前方案建议的 10） |
| 相似度 | L2 normalize 后的内积（cosine） |
| Dense 存储 | 每用户向量矩阵 + UnitRef 映射 |
| 缓存键 | `model + dimension + text_hash`，并按用户作用域管理检索 |
| Dense 不可用 | 立即回退 BM25；日志记 `dense_available=false` |

建议接口：

```python
class EmbeddingClient:
    def embed_batch(self, texts: list[str]) -> list[list[float]]: ...
    def embed_query(self, text: str) -> list[float]: ...

class DenseIndex:
    def build_or_load(self, user_id: str, units: list[UnitRef]): ...
    def search(self, user_id: str, query_vec, top_n: int) -> list[UnitHit]: ...
    def invalidate(self, user_id: str): ...
```

**索引与故障处理（强制）**：

1. 原始 JSONL 是事实源，vector/embedding/解析缓存均为**可重建派生数据**，例如 `data_store/v2/<user_hash>/`。
2. `manifest` 保存 `model`、实际 `dimension`、分块规则版本、源数据哈希、向量条数、构建状态；重启验证 manifest，否则重建。
3. 验证向量条数一致、维度正确、数据 finite（无 NaN/Inf）、可归一化；异常批次整体拒绝入索引。
4. **严禁在 `MemoryStore._lock` 内请求远程 embedding API**。在锁内仅取得一致的只读源快照，再在锁外索引/调用 API；发布索引时校验版本，避免 `/add` 并发写入导致旧索引覆盖新索引。
5. `/add` 后 BM25 路径仍应立即可以检索新数据；Dense 更新若异步，则语义查询可能短暂延迟，必须显式定义与测试该一致性边界。如果官方要求 Dense 也立即可见，应另行采用限时同步 embedding + 失败降级设计。
6. Dense API 超时、配额不足、无网络、鉴权失败，都不能使整个 `/search` 失败；返回仍符合既有协议。
7. 可配置 Dense 相似度最低可信门槛，但不要照搬通用阈值，须用本数据的正负例评估；无有效候选时允许返回空。

### 3.4 一项实施前必须确认的约束：评测环境是否允许调用 embedding

旧路线图写有“`oracle → replay → agent`，禁网”，同时指定远程 `text-embedding-v4`。这两件事可能冲突：

- **允许访问 embedding 服务**：可以在线计算文档与实时 query embedding。
- **完全禁止外部网络**：只有预计算文档向量**不够**，因为 Agent 可能发出从未见过的新 query，仍需为 query 编码。此时必须使用评测允许的本地 embedding 模型或已获准的服务；如果没有，应将 Dense 置为关闭并依赖 BM25 + Builder。
- 不能为了回放分数而给特定评测 query 偷偷预置金标准答案或硬编码 query embedding。

**前置门禁 G-Net**：在上线计划中先确认 embedding 的实际可用性、合法性、延迟与成本。若不满足，继续推进 V2.1，而不是让整个方案阻塞。

## 4. 模块三：Hybrid Fusion（RRF）

**融合对象是 unit，而不是直接融合整个 Parent 文本。**

设某个 `unit` 在 BM25 和 Dense 的名次分别为 `r_b`、`r_d`，则：

```text
RRF(unit) = (1 / (60 + r_b) if unit ∈ BM25 else 0)
          + (1 / (60 + r_d) if unit ∈ Dense else 0)
```

实现要点：

1. 两路先各自去重，按相同 `UnitRef` 合并。Dense 子块命中先投影到 canonical unit，同一通道内只保留最佳名次。
2. `rank` 从 1 开始；RRF 不直接比较 BM25 原始分与 cosine 分。
3. 单路不可用时仍可用现有一路（融合分数内部记录；Agent 不应依赖跨版本 score 绝对大小）。
4. 先从融合 unit 聚合为 Parent 候选，**V2.2 先沿用 Parent 最高 unit 分数**，避免同时修改 Parent 聚合策略。
5. 对每个 Parent 保留若干高相关 `anchor` 候选，供 Builder 提取同任务互补证据；**不能**仅凭“属于同一 Parent”就认定同一 bug。
6. 分数相同时用稳定的 Parent/message/offset 键打破并列，保证相同输入输出顺序可复现。
7. 召回 Top-N 和最终 `top_k` 是两回事：40/40 是检索 unit 的池子，`top_k` 限制最终 Parent 结果数。

建议函数：

```python
def reciprocal_rank_fusion(
    bm25_hits: list[UnitHit],
    dense_hits: list[UnitHit],
    k: int = 60,
) -> list[UnitHit]: ...

def rank_parent_candidates(
    fused_hits: list[UnitHit],
) -> list[ParentCandidate]: ...
```

## 5. 模块四：Evidence Builder（核心新增模块）

推荐新增 `src/evidence_builder.py`，不要继续使用简单前后滑块作为主策略。

### 5.1 内部证据对象

```python
@dataclass(frozen=True)
class EvidenceSpan:
    user_id: str
    parent_id: str
    message_index: int
    start: int
    end: int
    role: str
    kind: str             # problem/source/error/patch/test/summary
    file_paths: tuple[str, ...]
    symbols: tuple[str, ...]
    test_names: tuple[str, ...]
    task_group: str | None  # 可由规则得出的同任务分组；不确定则为 None
```

`EvidenceSpan.content` 不必复制到索引中；渲染时根据 Parent 原始 message 和 `start:end` 精确取回。

源文本、role、message 顺序仍以 JSONL 为准；分类、实体及 `task_group` 只是派生元数据。

### 5.2 六类工程证据如何识别

| 证据类型 | 典型特征 | 提取约束 |
|---|---|---|
| **Problem** | 历史用户描述、任务目标、issue 文本 | 仅原始 message 中确有的问题描述才能标为历史 Problem；当前 query 不能伪装为历史记忆 |
| **Source** | `def/class`、代码块、源码路径、`cat/sed` 工具输出 | 保留文件/符号/行号以及原文引用 |
| **Error** | Traceback、异常类型、断言、失败日志 | 无真实错误日志时不编造复现结果 |
| **Patch** | `diff --git`、`*** Update File:`、`@@`、明确的补丁块 | 强制校验相关文件/函数/问题；不能把其他任务 patch 拼过来 |
| **Test** | 测试命令、`pytest`、unittest、passed/failed | 区分“运行命令”“输出结果”“目标相关通过”，不能以任意 `PASSED` 宣称整体修复通过 |
| **Summary** | 关联任务的 assistant 最终总结 | 必须具有同任务文件/符号/问题联系；优先末尾总结，但不能仅因是最后一条就采用 |

**非常重要**：原始记忆中 `[tool_result]` 可以位于 `role="user"` 的 message 内。因此不能用 `role` 单独判别“用户问题”和“代码工具结果”。

### 5.3 同任务关联：核心安全规则

采用**anchor + 证据关系**，而不是“anchor 前后 N 条消息”。

1. **Anchor**：优先选择与 query 文件路径 / 函数符号精确匹配的 unit；没有精确标识符时使用 RRF 高排名语义证据。
2. **候选展开**：从 anchor 所属的**同一 Parent** 查找预解析的 `EvidenceSpan`；候选可不与 anchor 相邻。
3. **强关联优先**：
   - 同符号 + 同文件；
   - 直接修改该符号的 diff；
   - 与错误栈/测试目标对应的源文件和测试文件；
   - 同一清晰任务片段中明确指向上述补丁的测试/总结。
4. **弱关联不充分**：
   - 仅同 Parent；
   - 仅同一个通用目录（如 `astropy/`）；
   - 仅都有“fixed”“passed”等词；
   - 仅消息相邻、仅 embedding 相似。
5. **针对 patch / test / summary 提高门槛**：至少需要可信的文件/符号/任务联系；有歧义时宁可缺席，不拼出虚假的“完整修复故事”。
6. 允许对**同一个 evidence** 的重叠窗口合并；不同消息保留独立的溯源标识。
7. 同 Parent 中若包含多项任务，尽量以历史任务边界、文件/符号变更和工具操作链识别 `task_group`；识别不充分时不要强行合并。

**反例测试必须包含**：`_check_required_columns` 的 source anchor + 同 Parent 中另一个 `to_pandas()` 任务的真实 patch。Builder 应**拒绝**把这两个证据标为同一修复。

### 5.4 选择与排序

Builder 不是“每种类型都填满”，而是选择**相关性高且互补**的证据：

```text
先保 anchor/source/problem（帮助 Agent 定位）
→ 再按当前任务选 error / patch / test
→ 最后选能够对应同一任务的 summary
→ 相似重复片段去重
→ 在全局与 Parent 预算内输出
```

建议模板顺序与用户架构图一致：

```text
Problem → Source → Error → Patch → Test → Summary
```

- Bugfix 类 query 可以在预算选择时适当提前 Error/Patch/Test；对外渲染顺序保持固定，便于 Agent 阅读。
- 若只找到 Source，则只输出 Source；**不造 Patch/Test/Summary 的正文**。
- 证据原文按源 offset 提取，源代码片段应尽量包含完整函数与关键行；diff 尽量按 hunk 截取，Traceback 尽量保留首尾关键行。
- **原则上不要输出自动生成的“根因已经确认”“该补丁已验证”等结论**。根据原文无法证明的诊断只可作为离线分析，不冒充记忆证据。

### 5.5 预算分配

1. 全局硬预算：60,000 **字符**（不是 tokens），包含模板标签、换行等所有输出。
2. 每个 Parent 初始目标 4,000–8,000 字符；软上限可配置 12,000–18,000；最终不得突破全局预算。
3. 分配两轮：
   - **第一轮**：为每个已选择 Parent 预留最有价值的 anchor/关键源码，避免第一个长 Parent 吞完全部预算。
   - **第二轮**：给相关 Parent 的 patch/test/关联上下文追加剩余预算，优先证据互补而非重复。
4. 截断只在完整行、完整 diff hunk 或完整错误段边界进行；过大的代码块应保留相关函数/上下文，不机械切断重要关键行。
5. 预算不足时减少次要 Parent 或弱关联证据；不输出只剩标题的空章节。
6. 组装前后都校验 `len(content)`；最后对 `sum(len(...))` 做硬校验。

### 5.6 对外结构化渲染格式

因为官方 `/search` 要求 `content` 是字符串，推荐轻量、可读、节约字符的文本结构，而不是改成 JSON object：

```text
[problem | m=12]
<来自同一 Parent 的原始问题片段>

[source | m=75 | astropy/timeseries/core.py | _check_required_columns]
<来自原始 message 的源码片段>

[error | m=81]
<来自原始 message 的错误堆栈>

[patch | m=100 | astropy/timeseries/core.py]
<来自原始 message 的 diff>

[test | m=109]
<来自原始 message 的测试命令及输出>

[summary | m=115]
<来自原始 message 的总结>
```

上面只是**模板示意**，`m=12/81/100/109/115` 为示例序号，不代表本次 Astropy 实际存在这些消息。**各段只有在存在、相关且可回溯时才渲染**。首选正文引用简单标签，不加内部 debugging 的 token/span ID。精确偏移等详细来源保留在服务端调试日志/追溯数据中。

**缺口状态的处理**：可以在内部 diagnostics 记录 `patch_not_selected` 或 `no_verified_target_test_found`。对 Agent 的证据正文默认省略不存在的章节；除非能证明全池缺失，否则不能把“本次没召回”表述为“历史中绝不存在”。

## 6. 模块五：Structured Engineering Context

### 6.1 输出什么

这是检索层最终交付的“**工程证据上下文**”，不是生成式答案。它应帮助 Agent 快速回答：

- 之前发生了什么问题？（如原始 Problem 存在）
- 关联到什么文件/函数？（Source）
- 实际看到哪些异常？（Error）
- 历史上有没有**同一问题**的代码修改？（Patch）
- 什么测试真的跑过？结果如何？（Test）
- 历史讨论最后怎么总结？（Summary）

### 6.2 两种合法状态

**状态 A：历史修复证据齐全。** 同一任务链里有 patch、test 和可关联 summary，返回带出处的多证据包。Agent 可以尝试复用，但仍需检查当前仓库和运行测试。

**状态 B：只有诊断证据。** 例如本次 Astropy required-columns 样例，返回 `messages[75]` 的源码相关片段；缺少该问题 patch/test 时不伪造章节。Agent 根据源码自主定位/修复。

如果某 Parent 只有弱语义关联、无法对应具体工程问题，可舍弃该 Parent，而不是硬凑结构。

### 6.3 Agent 不应收到的东西

- 当前问题并不存在于历史中的“标准补丁”；
- 从另一个 bug 借来的测试结果；
- 仅凭 summary 猜测的“全部测试通过”；
- 由检索层生成的、无法追溯原始消息的根因结论；
- 内部相似度/阈值细节和大量重复原文（浪费上下文）。

## 7. 模块六：Agent

**职责明确切分：**

- 检索服务：发现与组织历史证据；不执行补丁、不调用生成式 LLM 输出最终修复。
- Agent：理解证据 → 打开当前仓库 → 识别当前版本差异 → 修改代码 → 运行测试 → 输出工程答案。

不能保证结构化返回一定提高官方得分，因此 Agent 层需要**真实 trace 验证**：

1. Agent 是否发起 `/search`、发出的 query 内容是什么？
2. Agent 实际收到哪个 Parent、哪几类证据、多少字符？
3. Agent 是否查看目标文件/函数？
4. Agent 最终有无修改、修改到什么位置？
5. Agent 是否执行了相关测试，测试通过/失败分别是什么？
6. 官方 F2P 是否通过、P2P 是否回退？

只有看到这条链路，才能判断是 Search、证据组织、Agent 推理、Agent 工具操作还是环境问题。

### 8.1 `MemoryStore.search()` 最终伪代码

```python
def search(self, user_id: str, query: str, top_k: int = 5) -> list:
    if top_k <= 0 or not query.strip():
        return []

    q = parse_query_features(query)

    # 锁内只取得一致的只读 snapshot/index version；网络与重计算在锁外。
    snap = self.get_search_snapshot(user_id)
    if snap.is_empty:
        return []

    # 双路召回；dense 出错时降级 BM25
    sparse = search_bm25_units(snap.bm25_index, q, top_n=40)
    dense = self.dense_service.safe_search(snap, q.raw, top_n=40)
    fused = reciprocal_rank_fusion(sparse, dense, k=60)

    # 排名与最后返回均以 Parent 为单位
    ranked_parents = rank_parent_candidates(fused)

    # 每个 Parent 多证据提取与关联；不跨 Parent 拼正文
    return self.evidence_builder.build_results(
        query_features=q,
        parents=ranked_parents,
        snapshot=snap,
        top_k=top_k,
        max_content_chars=60000,
    )
```

**注**：该段是待实现的接口设计，不是已在原源码里存在的函数；V2.1/2.2 的实验通过 feature flag 使用相应组件子集。

### 8.2 配置项建议

```bash
SEARCH_PIPELINE=legacy               # legacy | bm25_builder | hybrid_single | hybrid_builder
BM25_TOP_N=40
DENSE_TOP_N=40
RRF_K=60
EMBEDDING_ENABLED=false
EMBEDDING_MODEL=text-embedding-v4
EMBEDDING_DIM=1024
EMBEDDING_BATCH_SIZE=8
EMBEDDING_TIMEOUT_SECONDS=8
EVIDENCE_PARENT_TARGET_CHARS=8000
EVIDENCE_PARENT_SOFT_MAX_CHARS=16000
MAX_RESPONSE_CONTENT_CHARS=60000
```

`EMBEDDING_ENABLED=false` 为初始安全默认；确认端点和评测约束后开启。用原 `legacy` 模式一键回滚。

## 9. 版本实施顺序（保留可归因性）

| 阶段 | 运行系统 | 唯一核心变量 | 输出物 | 判断重点 |
|---|---|---|---|---|
| **Step 0** | 静态审计 | 无 | `answer_evidence_audit` | 区分完整历史修复 / 仅诊断上下文 / 无相关材料 |
| **V1.1** | 现有 BM25 + 单 unit | 基线 | 基线日志与 Agent 得分 | 当前症状 |
| **V2.1** | BM25 + Evidence Builder | **证据组织** | `evidence_builder.py`、组装单测 | 高命中时是否明显提高可用上下文 |
| **V2.2** | BM25 + Dense + RRF + 单 unit | **召回通道** | embedding/index/fusion | Dense 是否增加有用候选，成本是否可接受 |
| **V2.3** | BM25 + Dense + RRF + Evidence Builder | **组合** | 最终 Pipeline + smoke | 两者是否叠加改善 Agent 完成率 |

### 调整旧 G0 定义（非常重要）

旧文档认为“没有目标历史补丁就停止所有版本实验”。为了适应“让 Agent 基于证据自主修复”的新目标，建议改为三态：

- `historical_solution_present`：有同任务补丁/测试，可验证**答案复用能力**；
- `diagnostic_evidence_only`：有相关源码/错误，但缺目标补丁；允许验证**Agent 自主修复能力**，但不能把缺补丁算成 Builder 的“漏召回”；
- `no_relevant_evidence`：没有相关材料；如实报告数据缺口，不能通过参数调优制造证据。

这不会改变数据事实，只是把“评测目标”从**仅复用历史补丁**扩展到**用有效历史上下文辅助 Agent 解题**。

### 版本门禁

- **G1（V2.1）**：正对照的 patch/test/source 不再被单 unit 丢失；无关补丁不会误拼；目标案例的源码覆盖不退化；Agent 端至少可读取结构内容。
- **G-Net / G2（V2.2）**：模型在评测环境真实可用；Dense 相对 BM25 提供有效新增证据、改善任务完成率或有明确召回收益；故障回退与成本可接受。
- **G3（V2.3）**：相同数据/query 下，Agent F2P 优于或至少不劣于强基线；证据归因正确；没有跨任务污染、隐私问题或严重延迟回退。
- 不满足门禁就保留表现更好的阶段，不因架构图漂亮而强制上线 Dense。

## 10. 测试清单（开发必须交付）

### 10.1 API / 数据契约

- [ ] `/add` 请求字段、幂等行为、Parent ID 计算不变。
- [ ] `/search` 响应字段与类型不变；`content` 是字符串。
- [ ] `len(data) <= top_k`，每个 Parent 至多一次。
- [ ] `sum(len(content)) <= 60000`，包含所有标签。
- [ ] 同一用户只返回该用户的 Parent；跨用户相同 Parent ID 不越界。
- [ ] 空 query、无相关数据、Dense 不可用的行为符合各版本约定。
- [ ] `reset()` 清理派生索引，重启后向量与 JSONL 对齐。

### 10.2 Evidence Builder

- [ ] 完整源码/工具结果能按 `message_index/start/end` 回溯原文。
- [ ] 一个 Parent 的 source+patch+test+summary 正确组装、不重复。
- [ ] **跨任务负例**：required-columns 的源码不拼接 `to_pandas()` patch/test。
- [ ] 缺 patch/test 的任务只输出有出处的 evidence，不生成“已修复”。
- [ ] 历史 `role=user` 的 `[tool_result]` 能识别为源码/测试证据。
- [ ] diff hunk、Traceback 和关键函数内容尽量完整；预算不足可选择不返回低价值证据。
- [ ] 同一 Parent 的重叠窗口合并；不同 Parent 不合并正文。
- [ ] 查询极短、模糊、跨项目时不会因强制填模板而扩大噪音。

### 10.3 Dense / RRF

- [ ] 相同输入向量统一 L2 归一，cosine/点积一致。
- [ ] 请求维度错误、NaN、Inf、批次条数错误均被拒绝。
- [ ] 模型/维度/分块版本改变后会触发重建，不复用错误缓存。
- [ ] Dense 子块回映到 BM25 canonical unit，RRF 去重正确。
- [ ] 同一 query 重复请求排序稳定；相同源 span 只入一次。
- [ ] Dense 断网/超时/限流时安全降级，不在 Store 锁内做网络调用。
- [ ] `/add` 与 `/search` 并发时不会丢数据或发布过期向量索引。
- [ ] 只有 Dense 语义相关、BM25 无重叠的 query 能返回**确有来源**的候选。
- [ ] 有充分负例，低语义相关时不过度自信返回无关证据。

### 10.4 官方 Agent 评测

按项目已有测试条件跑 `oracle → replay → agent`；**这三个模式是原 roadmap 的评测约定，相关执行脚本不包含在当前 `src.zip`，需在实际工程环境确认**。

对每一版记录：

| 指标 | 解释 |
|---|---|
| Agent F2P / P2P | **上线主指标** |
| 完成目标工程任务数 | 按独立问题计数；不要把同题 30 次查询当作 30 个修复任务 |
| 证据 Recall@N | 正确证据是否进入召回池 |
| 返回证据覆盖 | 已存在证据中 source/patch/test 等被带回比例 |
| 证据串题率 | 把无关补丁/测试误组装到当前任务的比例，目标 0 |
| Source 可追溯率 | 返回原文可回查 offset 的比例，目标 100% |
| 字符数和空结果率 | 控制输出质量与上下文污染 |
| p50 / p95 延迟 | 端到端检索时延及 Dense 额外成本 |
| Dense 可用率 / 降级率 | 外部依赖与线上稳定性 |

**公平性要求**：同一份 memory、同一组 query、同一可用 Agent 环境；固定 git commit / image tag / 配置；不挑最好的一轮作为正式结果。若做多轮稳定性研究，事先固定轮数和汇总方法。

## 11. 开发里程碑和优先级

### P0：先获得“结构可用”的证据（V2.1）

1. 提取 `UnitRef` 与 `search_bm25_units()`；不破坏原 `legacy` 模式。
2. 完成 `EvidenceSpan` 规则解析与 Parent 内索引缓存。
3. 完成 anchor → 同任务关系关联 → 去重 → 内容预算分配。
4. 完成 `[problem/source/error/patch/test/summary | m=...]` 渲染。
5. 使用本次数据建立**正对照** `to_pandas()` 和**负对照** required-columns。
6. 跑结构单测与官方 Agent，对比 V1.1。

**交付条件**：真实的 patch/test/summary 可以正确聚合；不同任务绝不串题；缺补丁时也能交付有出处的诊断证据包。

### P1：增加语义召回（V2.2）

1. 完成 G-Net 评测/部署可用性检查。
2. `EmbeddingClient` + `DenseIndex` + manifest/缓存/无网络降级。
3. 完成 `UnitRef` 对齐、Dense Top-N、RRF。
4. 独立以“混合召回 + 原来单 unit 返回”测试新增召回收益。
5. 只有确认收益、成本可控才开启线上开关。

**交付条件**：确有 BM25 漏掉、Dense 找回的有用证据；不因外部 embedding 失败导致搜索中断。

### P2：组合与上线（V2.3）

1. 复用 V2.1 的 Builder 处理 V2.2 的 Hybrid 候选。
2. 控制 Dense 扩候选导致的预算稀释；必要时调整多样性选择，但不要顺手修改 Parent 排名算法。
3. 运行最终合约测试、回归评测、Agent smoke 与故障注入。
4. 默认先灰度/可回滚，再决定是否切换 `SEARCH_PIPELINE=hybrid_builder`。

**交付条件**：Agent 主指标有可核实的改善或明确不退化，同时保持 API、安全与可追溯契约。

## 12. 风险与纠偏

| 风险 | 典型表现 | 纠偏 |
|---|---|---|
| Dense 召回近义但无关任务 | 多了高相似错误补丁 | 关联证据必须有路径/符号/任务联系；降低对语义单因子信任 |
| Parent 内混杂多个任务 | `_check_required_columns` 拼上 `to_pandas` diff | 强关联门槛、task_group、明确负例测试 |
| 文档没有历史目标补丁 | 检索得到源码但无 Patch | 合法返回诊断包，让 Agent 独立修复；不伪造结果 |
| 模板固定章节过多 | 真实源码被空标题挤出预算 | 缺失章节默认省略，短标签 |
| 候选数量增加挤走好证据 | 提升 Recall 却降低 Agent F2P | 每 Parent 先保 anchor，按多样性和相关性分配两轮预算 |
| Embedding 服务在评测时禁网 | Dense 查询失败 | G-Net 前置；使用允许的本地 embedding 或 BM25 降级 |
| 旧索引与新 Add 不一致 | 新消息不能立即检索 | 版本化快照/失效/锁外构建，明确 Dense 更新时效 |
| score 语义改变 | 误把 RRF 当 BM25 分数调阈值 | 日志标记 pipeline/scoring version，不跨版本比较数值 |
| 为特定 smoke 过拟合 | 只在当前 Astropy 案例有效 | 通用 parser，独立正负对照，避免 query 特判 |
| 内部泄露用户数据 | 向量缓存或日志跨用户关联 | user 隔离、用户作用域索引、不在普通日志打印记忆正文 |

## 13. 完成定义（Definition of Done）

一次真正完成的 V2.3 改造，必须同时满足：

- [ ] **架构落地**：BM25、Dense、RRF、Evidence Builder 均有独立接口，可按开关启停。
- [ ] **结构完整且诚实**：存在的相关证据能正确组合；不存在的补丁/验证不被虚构。
- [ ] **原始证据可溯源**：所有引用能定位到 Parent/message/span，字符串原文未被擅自改写。
- [ ] **API 兼容**：官方 `/add`、`/search` 请求响应不变，`id` 仍是 Parent，`top_k` 与 60k 约束均通过。
- [ ] **隐私隔离**：不能跨 `user_id` 检索、混组或误用向量索引。
- [ ] **故障可降级**：Dense 不可用时仍可由 BM25 + Builder 返回；一键可回滚 V1.1。
- [ ] **效益被验证**：有独立任务级的 Agent F2P/P2P 结果及 trace，不只看 BM25/Dense Recall。
- [ ] **交付可复现**：代码 commit、模型配置、索引 manifest、镜像 tag、评测记录相互对应。

## 14. 最终结论

**应采用六层终态架构，但把“Evidence Builder”视为核心工程能力，把 Dense 视为互补的召回能力。**

- **V2.1**：先证明正确组织已有证据能帮助 Agent，而不只是扩大滑窗；
