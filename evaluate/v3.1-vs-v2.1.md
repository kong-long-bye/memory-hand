# V3.1 对比 V2.1：到底改进了什么

> 分支：`feat/v3.0-lite`（V3.1 = V3.0 精简版的落地实现）
> 数据：官方 31 条 /search 回放（relevant + noisy 两个 user，共 90 条返回结果）
> 生成方式：
> ```bash
> RETRIEVAL_MODE=v3_0 evaluate/.venv/Scripts/python.exe \
>   evaluate/export_search_qa.py \
>   --output evaluate/v3.1-search-qa.md \
>   --jsonl evaluate/reports/v3.1_search_qa.jsonl
> ```
> V2.1 基线来自 `evaluate/reports/v2.1_search_qa.jsonl`（同口径重跑）。

## 一句话结论

**V3.1 没有改召回、没有改排序，只改了"返回内容的组装与诚实性"**：
同样的 31 条检索、同样的 id/score/条数，内容体积减半，补丁从"埋在正文中段"
变成"开头就给 + 明确声明有没有答案"，并且用 False Solution 门禁挡住了
跨任务补丁污染。

## 1. 召回与排序：零变化（设计如此）

| 指标 | V2.1 | V3.1 |
| --- | --- | --- |
| 31 条检索 Top-1 id | — | **31/31 完全一致** |
| 31 条检索 Top-1 score | — | **31/31 完全一致** |
| 每条返回条数 | — | **31/31 完全一致** |
| 检索延迟（稳态） | 2–6ms | 2–6ms |

V3.1 只动 `EvidenceBuilder.render()`，BM25、索引单位、Parent 聚合、
`_select` 关联集合全部原样复用 V2.1。`RETRIEVAL_MODE=v2_1`（默认）时输出与
master 字节级一致，可随时回滚。

## 2. 内容体积：-50.1%

| | V2.1 | V3.1 |
| --- | --- | --- |
| 90 条结果总字符 | 897,744 | **447,974（-50.1%）** |

砍掉的是：与 focus 无关联的 patch/test/summary 分节（False Solution 门禁）、
按 status 收紧的预算（source_only/related_only 不再顶满 16k）。
**没有砍掉任何被绑定为"答案"的证据。**

## 3. 答案前置：补丁从中段挪到开头

统计"返回内容里含补丁（unified diff）的结果"中，diff 首次出现的位置：

| | V2.1 | V3.1 |
| --- | --- | --- |
| 含补丁的结果数 | 57/90 | 27/90 |
| diff 出现在前 2KB 内 | **0/57** | **27/27** |
| diff 位置中位数 | 8,252 字符 | **1,626 字符** |

V2.1 把 57 条结果都塞进补丁，但全埋在中段（Agent 按前缀截断时根本看不到）；
V3.1 只保留 27 条**真正绑定了 focus** 的补丁，且全部 answer-first 排在开头。
少的那 30 条正是污染源（见 §5）。

## 4. 诚实性：status 标注 + 声明，90/90 全覆盖

每条结果头部带 `[solution_status=...]`，末尾带英文 NOTE 声明。90 条结果的
status 分布：

| status | 全部 90 条 | Top-1（31 条） | 含义 |
| --- | --- | --- | --- |
| source_only | 58 | 24 | 只有修复前源码，**明确声明记忆里没有已验证补丁** |
| patch_available | 16 | 1 | 有绑定补丁，但没有绑定的通过测试 |
| verified_solution | 11 | 3 | 绑定补丁 + 绑定通过测试 |
| summary_only | 4 | 1 | 只有文字总结 |
| related_only | 1 | 1 | 弱相关，≤1000 字符 |
| （空） | 0 | 1* | *noisy user 无对应记忆 |

对 astropy-13033（required-columns）这类**记忆里根本没有答案**的检索，V2.1
返回 16k 混合内容让 Agent 自己猜；V3.1 返回 source_only +
"NO verified patch exists in memory for this problem"，Agent 不会误把
历史源码当成解法。**预期 F2P 仍是 0 分（数据缺口，检索无法返回没存过的
内容），但不再产生误导。**

## 5. 防污染：False Solution 门禁实测 + 审计中修掉 3 个真缺陷

T2 负对照（required-columns 检索禁止出现 to_pandas 任务的
`remove_indices`）：V2.1/V3.1 双模式回放均通过；31 条官方检索
**0 条出现跨任务补丁污染**。

审计过程中发现并修复了 3 个绑定缺陷（各带回归测试）：

1. **裸文件名碰撞**：query "fix core.py" 时，`astropy/timeseries/core.py` 和
   `astropy/io/ascii/core.py` 因裸名 "core.py" 相交被误绑定
   （官方 Search #23 实际触发）。修复：路径绑定只认含 `/` 的完整路径。
2. **多任务 summary 锚点投毒**：P0（460 条消息）的末尾总结
   "summary of all changes" 实体横跨 timeseries 与 io.ascii，作为 top 锚点
   时把 io/ascii 路径捐进 focus。修复：kind=summary 的 top 锚点只捐强符号、
   不捐路径。
3. **修复 2 的回归**：T4（ProgressBar）的 top 锚点是单任务 `[thinking]`
   note，被连带禁捐路径后 T4 从 patch_available 掉到 source_only。
   精化：只有 summary 不捐路径，note 照常捐。T4 恢复 patch_available。

## 6. T1 正对照：历史里真有答案时，答案第 84 个字符就到

T1（to_pandas KeyError）：V3.1 top-1 为 patch_available，
`remove_indices` 真实 diff 出现在**第 84 字符**；V2.1 同一检索的补丁在中段。
这是 V3.1 的核心收益场景。

## 7. 需要如实说明的边界

- **verified_solution ≠ 一定是当前问题的解**：required-columns 检索有 3 条
  top-1 标为 verified_solution，绑定的是同文件（timeseries/core.py）
  构造轨迹的历史补丁 m328/m331（`_init_from_list` dtype 修改 + 通过的
  test_timeseries.py），与锚点实体一致、溯源透明，但**不是**
  required-columns 的修复（该修复不在记忆里）。status 表达的是
  "证据链完整"，不是"这道题的答案"。
- astropy-13033 预期仍 0 分，改进在防误导而非提分。
- 端到端 F2P 以平台为准，本地只做检索侧指标。
